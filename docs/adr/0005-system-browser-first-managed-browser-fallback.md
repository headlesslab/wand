# Resolve the system browser first and download a managed browser only as a fallback

Upstream's `launcher.New()` downloads a pinned Chromium trunk build on every machine that has not cached it, never looks for an installed browser unless the caller opts in, and races Google's bucket, npmmirror and a Playwright URL that is dead off linux/arm64. wand's users deploy to domestic platforms and restricted networks where that download is slow, blocked or impossible (loong64, musl and windows/arm64 have nothing to download), so the launcher resolves a browser in this order: an explicit path (code option, `-wand=bin=` flag, `WAND_BROWSER_BIN`), then a system browser from an expanded discovery list, then a managed browser from the cache, downloading one only when nothing earlier is found and only on platforms where the pinned build exists. The default managed browser is the Target Chrome from Chrome for Testing (the `chrome` binary, `chrome-headless-shell` on request), with a Companion Chromium trunk build as a second browser source for deployments that need a BSD-licensed binary rather than Google Chrome under Google's terms. Both pins and the SHA-256 of every archive live in the one constant file the automated roll PR bumps per Chrome stable milestone, and the launcher verifies every download against those hashes whichever host served it. Download hosts are Google's buckets and npmmirror, probed concurrently with the fastest responder winning and the rest as fallback; Playwright's host is dropped. We accept that most users run a browser other than the Target Chrome (wand logs the mismatch after connecting rather than refusing, and sets no Chrome floor) and that a second pin doubles the roll's downloads and adds a full-suite CI run on linux/amd64.

## Considered Options

- **Pinned browser first** (upstream, Puppeteer, Playwright): reproducible wherever it works, but every machine pays a ~200 MB download, restricted networks wait for a timeout before any fallback, container images grow, and loong64, musl and windows/arm64 fall through to the system browser anyway.
- **System browser only** (chromedp): no hidden network access, but a fresh CI container or developer machine fails on first run instead of working.
- **Chrome for Testing as the only browser source**: one pin and one URL template, rejected because CfT binaries are Google Chrome under Google's terms rather than BSD-3 Chromium, which some deployments cannot accept.
- **Substitute builds where the Target Chrome is missing** (win64 under emulation on windows/arm64, Playwright's arm64 Chromium, a separate ≥153 pin for linux/arm64): rejected as a second version that is not the Target Chrome; the linux/arm64 gap closes when Chrome 153 reaches Stable on 2026-09-08, and the permanent gaps are Tier 2 or unsupported.
- **Domestic browsers in the discovery list** (lbrowser, Qianxin, 360, UOS): none is verified to accept `--remote-debugging-port`, so they stay out of the code; users on them set `WAND_BROWSER_BIN` or `Launcher.Bin()`.

## Consequences

- Configuration is code option, then `-wand=` flag, then `WAND_BROWSER_*` environment variables (`BIN`, `CACHE`, `HOSTS`, `DOWNLOAD`, `SOURCE`, `BINARY`), then discovery; upstream had no environment variables at all.
- The browser cache moves to `os.UserCacheDir()/wand/browser` (Linux `$XDG_CACHE_HOME` or `~/.cache`, macOS `~/Library/Caches`, Windows `%LocalAppData%`), keyed `chrome-<version>`, `chrome-headless-shell-<version>` and `chromium-<revision>`; go-rod's `~/.cache/rod` is not reused.
- The Companion Chromium is the newest trunk position at or below the Target Chrome's branch point present for all five of upstream's bucket prefixes (`Linux_x64`, `Mac`, `Mac_Arm`, `Win`, `Win_x64`); no linux/arm64 trunk build exists, so that source is unavailable there. Upstream's revision generator comes back from `393ac0d` with its selection rule changed.
- Chrome for Testing archives are pinned for all six CfT platforms (`linux64`, `linux-arm64`, `mac-x64`, `mac-arm64`, `win32`, `win64`); `windows/arm64` and `loong64` have no entry and are system-only.
- `HostPlaywright`, `RevisionPlaywright` and the monthly `check-revision` workflow go; the fastest-host race stays, and whether `fetchup` still implements it is settled with the dependency chain. A user-supplied version or revision has no recorded hash, so its download is not verified and says so in the log.
- A pre-fetch command (upstream's `lib/utils/get-browser` equivalent) remains for Docker builds and offline bundles.
- The baseline's first Target Chrome is chosen once Chrome 153 is Stable, so Tier 1 linux/arm64 has a downloadable build from day one.
- The published container image (`ghcr.io/headlesslab/wand`, linux/amd64 and linux/arm64) ships the Target Chrome pre-fetched at build time on both architectures, not the Companion Chromium, which has no linux/arm64 build; decided with the CI matrix (#20).

# Guard against orphaned browsers with OS primitives and a pipe tether, not leakless

Upstream kills the browser when the Go process dies through `ysmood/leakless`, which writes a prebuilt guard executable into the temp directory (6.33 MB of base64 embedded in `.go` files, built by upstream's CI, not reproducible) that Windows Defender, 360 and Tencent PC Manager flag intermittently (one such block killed the whole root test binary in the Chrome 152 run), that Falco alerts on in Kubernetes, that exists for only five targets so loong64 and windows/arm64 silently run unguarded, and whose `LockPort` hangs when the port is denied. Playwright and Puppeteer run no guard process at all: on Windows libuv puts the browser in a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and on Linux and macOS the only reaper is Chromium's own behaviour since M89 of exiting when the read end of `--remote-debugging-pipe` (fd 3) reaches EOF, which is why Puppeteer's default WebSocket mode leaks the browser when its parent is SIGKILLed and Playwright, which always uses the pipe, does not. wand deletes leakless. The launcher assigns the browser to a kill-on-close job object on Windows (`golang.org/x/sys/windows`); on Linux, every GOARCH included, it sets `Pdeathsig` SIGKILL with `Setpgid` from a goroutine that has locked its OS thread; and on every POSIX platform it also passes `--remote-debugging-pipe` with fds 3 and 4 open and held, unused, by wand (the pipe tether), so that Chromium exits by itself when the wand process dies and the kernel closes the descriptors. CDP traffic stays on the WebSocket and `Launch()` still returns a URL, since Chromium starts the pipe and port handlers independently. `Launcher.Leakless(bool)` keeps its name and defaults (on in `New()`, off in `NewUserMode()`) as the switch for the guard.

## Considered Options

- **Keep leakless, default on or off**: retains the false positives, the Falco alerts, the non-reproducible binaries, the five-target ceiling and the `LockPort` hang; default-off leaves no protection at all on the path most users take.
- **OS primitives only** (chromedp: Linux `Pdeathsig`; runZeroInc: `Setpgid` + `Pdeathsig` + a process-tree sweep): macOS has no parent-death primitive, so a SIGKILLed driver leaks Chrome there; the tether closes exactly that gap for Chromium 89 and later at the cost of one flag and two descriptors.
- **Re-executing the user's own binary as the guard from an `init()` hook** (rod #602): every platform and no dropped file, but a library's `init()` cannot stop sibling packages' `init()` side effects (database connections, listeners) from running again inside the guard process.
- **The pipe as the protocol transport** (Playwright): changes `lib/cdp` and the `Launch()` / `ControlURL` contract; left to API modernization.

## Consequences

- Coverage: Windows is kernel-level whatever the browser; Linux has `Pdeathsig` whatever the browser plus the tether; macOS has the tether only, so Chromium older than 89 or a browser that rejects the flag degrades to the process-group kill on normal exit, which is chromedp's level.
- Chrome 113 and later abort at startup when fds 3 and 4 are not open, so the flag is passed only with both descriptors created (`cmd.ExtraFiles`, which is POSIX-only; Windows relies on the job object and passes no pipe).
- Branded Chrome refuses both the pipe and the port on the default profile (the Chrome 136 and later `NewUserMode()` case from the test run), so the guard adds no failure that the port did not already have.
- The test suite gets browser cleanup on failing runs on all Tier 1 operating systems: the test binary exiting closes the job object and the descriptors and fires `Pdeathsig`, which upstream's `TestMain` left to leakless.
- `Pdeathsig` fires when the creating thread exits, not the process, so the goroutine that starts the browser locks its OS thread for the browser's lifetime; the setting does not propagate to Chrome's own child processes, which the process-group kill and Chrome's own shutdown cover.
- rod #720, #1214, #1229 and #1232 and leakless #12 are resolved by removal; `leakless.LockPort` goes too (ADR-0006).
